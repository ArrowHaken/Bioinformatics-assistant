# 没有现成脚本时怎么办

库里查不到匹配「环境 × 需求」的脚本时，走这里。
**只有走到这一步才需要 AI 生成新脚本。**

---

## 一、先别写脚本，先定位瓶颈

新脚本不能凭感觉写。先做小范围探针：**只跑第 1 个样本**。

看它卡在哪：

| 现象 | 瓶颈 | 下一步 |
|---|---|---|
| 报 `cannot allocate vector of size X Gb` | 内存 | 走分块改写，不要降精度 |
| 报缺包 / 版本不符 | 依赖 | 先补依赖；补不了才考虑改实现 |
| 跑得动但极慢 | 算法/实现 | 找同口径的加速实现（进库三） |
| 读不进数据 | 路径 / 格式 | 先修输入，别动算法 |

**一句话：先把瓶颈说清楚，再决定改什么。** 上来就重写整个流程，等于把已经验证过的部分也一起赌掉。

---

## 二、能改就改，别重写

优先级从高到低：

1. **找库里已有的**：是不是环境判错了？确认一下是不是已经有匹配的条目。
2. **改最小的一处**：像低内存适配那样 —— 原实现只改一行（距离矩阵改分块），
   其它一律不动。改得越少，等价性越容易证明。
3. **换等价实现**：同口径的加速版（比如让 Seurat 自己调 presto），必须逐列对拍。
4. **实在不行才重写**。

第 2 条是关键。`param_sweep_blocked.R` 就是范例：全文件只改了 1 行，
其余逐字保留，所以「等价」这件事可以用一句话讲清楚。

---

## 三、新脚本要过六条门槛才能入库

写出来、跑通了，**还不算入库**。

| # | 门槛 | 怎么算过 |
|---|---|---|
| 1 | 跑通 | 全流程无报错，产出所有预期文件。**只是必要条件** |
| 2 | 结果符合预期 | 与官方口径逐项对账，差异定位清楚 |
| 3 | 等价性有证明 | 做过性能改写必须附等价性测试（如分块 rdist：最大绝对差 0、排序一致） |
| 4 | 偏差已声明 | 脚本头部写明「改了什么、为什么、影响什么」 |
| 5 | 参数已定 | 所有阈值有确定值、来源可追，无「待确认」 |
| 6 | 可重复 | 同环境同参数连跑两次，结果一致 |

**反例（real case）**：presto 那次跑通、有结果、图也正常，速度快 600 倍，
但 logFC 尺度和官方不同（310 vs 1428），所以进不了库二，只能进库三草稿层，
标注「仅用于探索，不可用于交付数字」。

**跑通有结果 ≠ 可以入库。** 这条判断标准是对的。

---

## 四、写完要回写库表

新脚本进库时，同时改 `index.json`：

- 加一条 entry：环境、需求、路径、状态
- 状态先写 `draft`，过完六条门槛再改 `ready`
- 在脚本头部写清楚：从哪来、改了什么、等价性怎么证的

**库表和文件必须一致。** 只丢文件不改表，下次查表就查不到；
只改表不丢文件，查表会取到一个空目录 —— 那就是假可用，比没有更坏。

---

## 五、这一步之后

新脚本入库后，环境 × 需求 就多了一个坐标。
下次同样的环境、同样的需求，查表直接取得到，不用再生成一次。

**库是靠这样一格一格长起来的，不是一次建完的。**
