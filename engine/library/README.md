# 脚本库

按「环境 × 需求」锁定要取哪一套。不是文件夹集合，是一张表。

库表在 `index.json`。**改库先改库表**，不要让文件和表脱节。

---

## 一、两个大类

### A 代码处理（数据处理环节）

| 条目 | 是什么 | 平时住在哪 |
|---|---|---|
| `A_official_E2_D1` | 甲方原生脚本（第一套） | **跟数据放在一起**，在对方电脑上 |
| `A_adapted_E1_D1` | 低内存适配脚本（第二套） | 只在库里。内存不够时取这套 |
| `A_fallback` | 没有现成脚本时怎么办 | 只在库里。走这里才需要 AI 生成新脚本 |

### B 分析绘图（分析与交付环节）

参考表 / marker 词典 · 六套图 · PPT · 报告提取。

**这一类在任何电脑上都查不到** —— 它本来就不属于别人的机器，必须从库里取。

---

## 二、取用规则

1. **先做容量预检**，判定环境（内存、系统、包）。
2. **A 类分三步判**：
   - 本机有甲方脚本 → 用本机的
   - 本机没有、但环境满足 `requires` → 从库里取甲方脚本推过去跑
   - 环境都不满足 → 取第二套（低内存适配）
   - 三样都不成 → 走 `A_fallback`
3. **B 类一律从库取**，不看环境（只看 `requires`，比如 PPT 要 Python）。
4. 每次运行都写台账：**环境 / 需求 / 取的是哪一套**。

---

## 三、入库门槛（缺一条都不进库）

1. 跑通 —— 只是必要条件，不是充分条件
2. 结果符合预期 —— 与官方口径逐项对账，差异定位清楚
3. 等价性有证明 —— 做过性能改写必须附等价性测试
4. 偏差已声明 —— 与官方不同的写法，脚本头部写明「改了什么、为什么、影响什么」
5. 参数已定 —— 所有阈值有确定值、来源可追，无「待确认」
6. 可重复 —— 同环境同参数连跑两次，结果一致
